Architecture and data flow

Four components and one rule: the agent owns every word the shopper reads, the application owns every fact on the screen, and the two meet through three tools with fixed contracts. This chapter names the components, traces one turn end to end in both directions, and says what happens when each link fails.

The components #

ComponentResponsibilityKey fact
Browser connectorOwns the conversation panel, executes the two client tools, renders only verified output.Client tools run in the shopper's browser over same-origin, search-only routes.
App serverOne validating proxy: schema-checks every request, pins credentials server-side, forwards to the agent and the indices.Search-only credentials never reach the browser.
Concierge agentInterprets the request, decides each turn, writes every shopper-facing word.Hosted by Agent Studio; model claude-sonnet-5.
IndicesProducts (prod_catalog + a newest-first replica), education (blog), policy (help_content).Strictly read-only to this system.

The server routes #

The storefront talks to exactly one origin. The server accepts seven routes, validates every body against a strict schema, and forwards to Algolia with the search-only key:

RouteUsed byPurpose
POST /api/chatConversationStreams one agent turn; enforces the tool-sheet guard first.
POST /api/searchAgent search tool, chip refinementMulti-query read-only search across the six catalog views.
POST /api/facetsVocabulary toolingSearch-within-facet queries on eight whitelisted facets.
GET /api/products/{id}Both client toolsOne exact catalog record; the identity is validated, the fetch is exact-ID.
GET /api/catalog-vocabularyRequirement enforcementThe live facet vocabulary, derived from the index on a 12-hour TTL.
POST /api/agent-product-refreshExact refreshRead-only exact-ID product facts for a set of object IDs.
GET /api/healthOperationsLiveness plus the tool-sheet guard status.

Search requests disable analytics, click analytics and A/B testing at the proxy, so a demo turn leaves no analytics trail. Bodies are capped at 2 MB, requests carry a correlation ID, and the upstream waits at most 15 seconds for response headers and 30 seconds between stream chunks before the turn fails honestly.

One turn, end to end #

  1. The send. The browser captures the shopper's message and builds the turn's metadata: the mission and turn identifiers, the accepted shopping facts (a compact JSON of requirement, preference and context facts with scope, strength, certainty and status codes, split into 900-byte chunks) and the chip selections the shopper has live on screen.
  2. The gate. The server validates the request, then compares the tools the agent declares with the tools this build answers. On a mismatch it returns a labelled error instead of an agent that appears to fail.
  3. The search. The agent builds one search: every named material, purity or gemstone becomes a facet filter with its verbatim vocabulary value from the search tool's own description, alongside the query words. The platform executes it against prod_catalog (already filtered to in-stock pieces) and streams the hits and facet counts back.
  4. The curation. The agent picks 9 to 12 pieces from the streamed result, best first, plus up to three facet attributes worth showing as chips, and calls present_products. That tool runs in the shopper's browser: it reads the requirement from the shopper's own message (never from a model-quoted field), resolves it against the live vocabulary, and checks every pick against the piece's actual record.
  5. The floor. If fewer than six verified pieces survive, the tool backfills from the streamed search's remaining hits with the identical checks; if the pool is exhausted, it runs one more facet-filtered search itself. Nothing enters the shelf without passing.
  6. The reply. The agent writes its answer from the verified list the tool returned, and the whole turn streams to the page: text, tiles, chips. The panel renders the tool's verified list, never the raw search stream, so a piece the tool dropped can never appear.
  7. The refinement. A chip tap filters within the turn through the same-origin search proxy; the next level's values come from the refinement's own facet counts. A follow-up question about one specific piece sends refresh_products for its exact record, so fresh facts replace cached ones.

Session state #

Continuity rides in the turn metadata, not in a server-side session. The accepted facts travel as a compact JSON: each fact is an ID, a field, a value, a scope (mission, item, recipient or component), a strength (requirement, preference or context), a certainty (explicit or tentative) and a status. The agent reads it as state, never as product evidence, and the chip selections ride beside it so a later search applies what the shopper already narrowed on screen.

How each link fails #

FailureBehavior
Agent declares an unknown toolThe tool-sheet guard returns a labelled tool_sheet_mismatch error on the chat route; the health route shows it. No silent fallback.
Upstream silent or slowThe headers and stall deadlines end the turn as an honest transport notice inside the shopper's reasonable wait.
Search returns nothing usefulThe agent says what the catalog does not have and offers the nearest in-scope action; the shelf never pads with wrong pieces.
A client tool cannot completeThe tool returns a structured error outcome; the agent decides what to tell the shopper. The application never authors agent speech.
A guardrail category tripsThe category's fallback notice replaces the content; the agent's instructions forbid claiming a guardrail pass as proof of anything.

The dividing line runs through everything: the agent generates the language; the application enforces the facts. Tool outputs are structured data, validation never writes shopper-facing text, and fixed notices exist only for genuinely fixed things like transport failures and guardrail fallbacks.
