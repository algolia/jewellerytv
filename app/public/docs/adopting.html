Adopting it

This documentation describes a working reference build, not a shrink-wrapped product. Adopting the experience on another jewelry site means standing up the same four components against your own catalog and your own voice. This chapter lays out what you bring, what you configure, the order to do it in, and an honest split between what is reusable and what is yours to write.

What you bring #

  • A product catalog in Algolia. The experience leans on clean, filterable facts: material and purity, gemstone and pearl names, brand. The whole verification and narrowing design assumes the catalog's facet values are trustworthy, because titles are not. If your catalog's material facts live only in titles, the first job is the data, not the agent.
  • Education and help content, if you want those answers. The reference build keeps three corpora separate: products, jewelry education (a blog corpus with canonical URLs) and service policy (help articles with canonical URLs). Each corpus is optional; each one you include needs reviewed content and real links, because the agent may only cite what it retrieved.
  • A storefront. Any site that can host a conversation panel, a product canvas and a few same-origin routes. The reference UI is React; the contracts it talks are plain JSON over HTTP.

What you stand up #

ComponentWhat it takes
The agentAn Agent Studio agent: system prompt, instructions, tool sheet, guardrail. The reference texts (chapter 7) are the starting pattern; the voice, evidence classes and worked examples should be rewritten for your store's voice and your catalog's vocabulary.
The search toolStatic tool-sheet entries for your indices, with the verbatim facet vocabulary written into the tool descriptions. This is what makes "copy values, never compose them" enforceable.
The client toolsBrowser executors for present_products and refresh_products against the contracts in chapter 4. The reference implementation is the pattern: shared record reader, per-tool checks, structured outcomes.
The proxyOne same-origin server with the validating routes of chapter 3, holding your search-only key server-side and enforcing the tool-sheet guard.

The order to do it in #

  1. Prepare the data. Verify the material, gemstone and brand facets exist and carry clean values. Everything downstream copies from them.
  2. Write the tool sheet. Fixed indices, in-stock pre-filter, bounded page sizes, verbatim vocabulary in the descriptions. Nothing unlisted.
  3. Adapt the prompts. Start from the reference texts; replace the voice rules, the worked examples and the evidence classes with your own; keep the four laws of chapter 4, which are architecture, not style.
  4. Build the client tools and the proxy. Port the two executors and the seven routes; keep validation strict and credentials server-side.
  5. Wire the guard. The tool-sheet check that refuses to run a chat turn when the agent declares a tool the app cannot answer. It turns a class of silent failures into one labelled error.
  6. Test connected, then promote. Test on a development agent through the real UI with fresh phrasings (completion caches are keyed to exact literals), then promote the tested definition to the production agent by script, never by hand-editing the live side.

Reusable versus bespoke #

Reusable as architectureYours to write
The division of labor: model picks, tool verifies, app renders.Your voice: the role, tone and worked examples in the instructions.
The tool contracts and the shelf-floor mechanics.Your vocabulary: which attributes carry material, stone and brand facts.
The validating proxy and the tool-sheet guard.Your starter questions, grounded in your own search analytics.
The guardrail categories and fallback pattern.Your evidence classes: which corpora answer education and policy, and their link rules.
The promotion, verification and rollback discipline.Your boundary wording: what your store can and cannot claim.

Operating rules worth keeping #

  • The catalog is read-only. No agent or application change should ever write to index records or settings. Everything the experience needs from the data, it reads.
  • One definition, two agents. A development agent for testing, a production agent for the public site, identical definitions, promotion by script with a recorded rollback snapshot.
  • Verify on the real surface. A unit test or an API trace does not establish shopper acceptance: capture the rendered screen, the network calls and the tool receipts from a real browser turn.
  • Watch the health route. It reports liveness and the tool-sheet guard status; a mismatch there means the next chat turn would fail loudly, by design.
